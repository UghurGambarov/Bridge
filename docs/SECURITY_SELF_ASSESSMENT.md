# Bridge — Security self-assessment

> SANDBOX prototype — fictional institutions, simulated accounts and FX rates. This document is submission item 5: permission-tier implementation and the known-risk list. Sections marked _auto_ are regenerated by `make docs` from `config/rules.yaml`, `evidence/scenario_report.json` and `docs/known_risks.yaml`.

## 1. Scope and method

**What we assess.** The Bridge agent pays university tuition abroad for a Chinese family. Its job is to read untrusted documents, verify the payee, enforce FX-quota rules and complete payments under human approval. The assets we protect are the family's money (sandbox CNY balance), the payer's personal FX quota, the integrity of payee details, the integrity of the evidence trail, and the family's personal data.

**Core assumption.** The language model is **untrusted**. Every guarantee below must hold even if the planner model is fully compromised. We test this with a `malicious` planner that ignores its instructions (cases A-10 to A-13).

**Method.**
- Threat modelling with STRIDE.
- Mapping to the OWASP Top 10 for LLM Applications (2025).
- Unit tests for every rule ID, with an allow test and a deny test where the rule applies.
- A scenario suite of 39 end-to-end cases, each on a fresh database through the real API.
- A known-risk register.

**Trust boundaries.**

| Boundary | Untrusted side | Control |
|---|---|---|
| Documents → system | invoice PDFs, emails, chat messages (may hide text or instructions) | deterministic detectors, quarantined extractor (no tools, strict JSON schema), raw text never reaches the planner |
| Planner model → tools | every tool call the model proposes | `policy.authorize()` — the single choke point (allow / deny / require_approval) |
| Agent → money | `execute_payment` | digest-bound human approvals, re-checked at execution; the bank refuses without a matching policy decision |
| Operator → system | freeze, clock, reset (privileged) | every action audited (production: operator authentication — R-14) |

## 2. The five security patterns

1. **Dual-LLM / quarantine.** The planner never sees raw untrusted text. The extractor model has no tools and must return JSON that Pydantic validates (extra fields forbidden). Free-text fields are sanitised before the planner sees them, and account numbers are masked. Pasted chat text is quarantined as a document.
2. **A single choke point.** `backend/app/security/policy.py::authorize()` evaluates every tool call: allow-listed tools, schema-validated arguments, tier rules. Every decision is written to the audit log. No tool runs without it.
3. **Capability restriction.** Payment tools accept only a `payee_channel_id` from the verified registry. Any argument that looks like an account number, IBAN or wallet address is refused (`T4-007`), so the model cannot type a payee.
4. **Human approval bound to a transaction digest.** The digest is SHA-256 over the canonical intent. Each approver's device signs `HMAC(key, digest:nonce)`. Nonces are single-use, expire after 15 minutes and are tied to one intent and one device. Execution recomputes the digest from the current database state. **The agent has no approval tool.**
5. **Tamper-evident audit.** `hash = sha256(prev_hash + canonical_json(entry))`. Anyone can verify the chain in the Evidence Center. The tamper simulation edits a *copy* and shows exactly where the chain breaks.

## 3. Permission tiers

| Tier | What the agent may do | Bridge example | Conditions |
|---|---|---|---|
| **T0 Read** | look and explain | balance, quota, Chinese summary, risk analysis | always |
| **T1 Prepare** | draft, never send or execute | payment intent in `draft`, document list, verification-email draft | never executes |
| **T2 Act within limits** | execute alone under preset rules | monthly allowance to Li Wei's own verified account | same-name verified payee; ≤ USD 2,000 per transaction; ≤ USD 3,000 per rolling 30 days; payer quota available; risk LOW; not frozen |
| **T3 Act with approval** | execute only after humans approve | tuition, accommodation, deposits, anything above the T2 caps | approvals from payer **and** student (configurable), bound to the digest, ≤ 15 min old, single-use; payee registry-verified; risk not HIGH; not frozen |
| **T4 Forbidden** | never, even if asked | uncle's quota, "tuition" to a personal account, crypto | refused with the rule ID and the lawful alternative |

**Why two approvers.** The mother pays, and Li Wei can check the fee on his university portal. That second check is exactly what would have stopped the "real admission + fake fee payment" agency fraud. Setting `T3-001.params.required_approvers: [payer]` in `rules.yaml` switches to mother-only approval (covered by `test_mother_only_configuration`).

## 8. Residual risk and the production path

- **The policy engine blocks wrong actions; it cannot stop wrong wording.** A compromised model could still write a misleading sentence. The mitigations: every figure is shown on a code-built card, AI text is labelled, and refusals come from the deterministic request guard (R-05).
- **Approvals are as strong as the devices.** The prototype keeps an HMAC key in the browser. Production uses WebAuthn / passkeys, and binds the approval prompt to the bank's own app (R-09).
- **The registry is the trust anchor.** Production needs a curated, signed registry, ideally fed by the universities or the partner bank (R-07).
- **Execution.** In production a licensed partner bank executes, with its own KYC/AML screening. Bridge is the verification and orchestration layer (R-03).
